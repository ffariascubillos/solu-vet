# DAILY_LOG_2026-09-01.md

1. Reviewed project status, roadmap, and tasks; confirmed the agreed next backend priority (Tutor update endpoint) before starting implementation.
2. User raised a data-quality issue ahead of that work: the Patient registration form's "Especie" and "Raza" inputs are free text, causing typos and inconsistent data.
3. Evaluated approaches with the user: free text with a suggested list (rejected), `species` as a Prisma enum + `breed` as a reference table (initial decision), and finally both `species` and `breed` as reference tables (final decision) — chosen because the user wants a future admin-only maintainer to add species/breeds without a database migration or app release, which a Prisma enum cannot support.
4. Confirmed with the user that both `speciesId` and `breedId` should be required on Patient (not optional) — every patient must have a species and a breed, with "Mestizo / Sin raza definida" seeded per species as the fallback for unknown breeds.
5. Confirmed it was safe to truncate the local `Patient` table (dev and `solu_vet_test`) before migrating, since there was no production data and `Tutor` records are untouched.
6. Added `Species` and `Breed` Prisma models; changed `Patient.species`/`Patient.breed` (free text) to required `speciesId`/`breedId` foreign keys. Ran the migration (`add_species_and_breed_reference_tables`) against dev and `solu_vet_test`.
7. Built the first Prisma seed infrastructure for the project (`apps/api/prisma/seed.ts`, `prisma.config.ts` seed wiring, `prisma:seed` script), seeding Perro/Gato with a small starter breed list per species.
8. Added read-only `GET /api/species` and `GET /api/breeds?speciesId=...` endpoints. Updated `createPatient` to validate that the species exists, the breed exists, and the breed belongs to the selected species (404/400 as appropriate). Added `include: { species, breed }` to all Patient read endpoints.
9. Updated mobile: new `Species`/`Breed` types, `getSpecies`/`getBreeds` service calls, a new reusable `SelectField` (built on `react-native-paper`'s `Menu`, no new dependency) replacing the free-text species/breed inputs in `PatientForm`, with breed options reloading whenever species changes. Updated Patient detail, Tutor detail, and Patient search screens to render `species.name`/`breed.name`.
10. Updated `apps/api/src/test/tutor-patient.api.test.ts` and `setup.ts` (seed the catalog once, keep it out of `cleanDatabase()`) and added new tests for species/breed validation and the new endpoints. All 21 API tests pass.
11. Verified `tsc --noEmit` (API and mobile) and `npm run lint -w apps/mobile` all pass after the change.
12. Updated `TASKS.md`, `PROJECT_STATUS.md`, and `ROADMAP.md`: marked this work done, and added a new deferred task — an admin-only Species/Breed CRUD maintainer, blocked on basic authentication with roles (which doesn't exist yet).
13. Gave the user a manual testing checklist for validating the Species/Breed change from a physical Android phone via Expo Go.
14. User hit `TypeError: Cannot read property 'name' of undefined` while testing on the phone. Root cause: `searchTutors` and `getTutorById` in `apps/api/src/modules/tutors/tutors.controller.ts` return nested `patients` via `include`, but that nested include was never updated to also include `species`/`breed` — unlike the Patient endpoints, which already had it. So Tutor detail and Tutor search returned patients with `species`/`breed` undefined, and the mobile screens crashed reading `.name`.
15. Fixed by adding `include: { species: true, breed: true }` inside the nested `patients` include in both `searchTutors` and `getTutorById`. Verified `tsc --noEmit` and the 21 API tests still pass after the fix.
16. User re-tested from the phone and confirmed Tutor detail and Tutor search (with nested Patients) now work correctly.
17. Next priority: resume the paused priority order — Tutor update/delete, then Patient update/delete, then basic authentication (which in turn unblocks the Species/Breed maintainer).
